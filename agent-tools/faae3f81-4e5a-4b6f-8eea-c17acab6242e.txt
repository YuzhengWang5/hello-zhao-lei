Adds a hidden `--temporary` flag, registered only on the commands the temporary preview-account deploy token can serve.

When the flag is not set, behaviour is unchanged. The original "set CLOUDFLARE_API_TOKEN" error path just gains a hint that `--temporary` is available.

| Scenario | Interactive | Non-interactive |
| --- | --- | --- |
| Logged out, `--temporary` passed | New: skips OAuth login. If a valid cached temporary preview account exists, reuses it and prints the claim URL. Otherwise prompts the user to type `yes` to accept the Terms of Service and Privacy Policy. Creates and caches a temporary preview account, prints the claim URL, and proceeds with the temporary account credentials. | New: skips OAuth login. If a valid cached temporary preview account exists, reuses it and prints the claim URL. Otherwise prints a Terms of Service and Privacy Policy notice. Creates and caches a temporary preview account, prints the claim URL, and proceeds with the temporary account credentials. |
| Logged out, `--temporary` not passed | Unchanged. | Existing behavior: errors because `CLOUDFLARE_API_TOKEN` is required in non-interactive mode. Changed copy: the error now suggests rerunning with `--temporary`. |
| Logged in, `--temporary` passed | New: does not create a temporary preview account. Warns that `--temporary` was ignored. Uses the existing Cloudflare account. | New: does not create a temporary preview account. Warns that `--temporary` was ignored. Uses the existing Cloudflare account. |
| Logged in, `--temporary` not passed | Unchanged. | Unchanged. |

### Scope

`--temporary` is registered per command on the set of commands the temporary deploy token can serve — Workers (`deploy`, `versions upload`, and related commands), KV, D1, Hyperdrive, Queues, and certificate commands. The set lives in a single `COMMANDS_SUPPORTING_TEMPORARY` list that mirrors `DEPLOY_TOKEN_PERMISSION_GROUP_IDS` in the provisioning worker. It is **not** a global option, so it doesn't appear on commands the token can't serve (Pages, R2, Workers AI, Pipelines, etc.) and doesn't pollute their `--help` or the generated command docs. A test asserts every entry in the list maps to a real registered command.

### How it works

- The flag is registered `hidden: true`, injected into the relevant commands by the yargs command registrar based on the `COMMANDS_SUPPORTING_TEMPORARY` allow-list.
- An `AsyncLocalStorage` frame holding `{ allowTemporary, override? }` is opened in `runWithAuthContext` immediately before the command body runs, so every awaited `requireAuth` / `getAPIToken` / `getActiveAccountId` call observes the same context without any parameter threading. The registrar sets `allowTemporary` in this context only for allow-listed commands that were passed `--temporary`.
- `requireAuth` is the single chokepoint for the temporary fallback: when the user is not logged in, the environment is non-interactive, and `shouldAllowTemporary()` is true, it fetches a preview account, installs `{ accountId, apiToken }` via `setAuthOverride`, and returns the account id as if it had been resolved normally.
- Downstream credential lookups (`getAPIToken`, `getActiveAccountId`) check the override first, so the rest of wrangler — completely unchanged — uses the temporary credentials transparently. The override also short-circuits `loginOrRefreshIfRequired`, so a stale stored OAuth token is never refreshed while a temporary account is active.
- The provisioning endpoint and the preview-account cache are both keyed to the active API environment, so targeting staging (`WRANGLER_API_ENVIRONMENT=staging`) mints and caches a staging account rather than reusing a production one.
- The preview account is cached per API environment (`wrangler-temporary-account.json` for production, `wrangler-temporary-account..json` otherwise) next to wrangler's other global config; cache is reused only while both `account.expiresAt` and `claim.expiresAt` are in the future, and is cleared on `wrangler login` / `wrangler logout`.
- If the user is already authenticated, `--temporary` is ignored and wrangler warns that the existing account is being used. In an interactive session, `--temporary` mints a temporary account after prompting for terms acceptance.

### Terms of Service

The `POST /provisioning/previews` request sends the required `termsOfService` and `acceptTermsOfService` fields. Before minting, `ensureTemporaryTermsAccepted` prompts for explicit acceptance in interactive sessions, or logs a terms notice and continues in non-interactive ones.

### Pages refactor

Six Pages `requireAuth` call sites (across five command files) previously short-circuited with `getCloudflareAccountIdFromEnv() ?? (await requireAuth(...))`. These now call `requireAuth` with a conditional spread so the cached `account_id` from `pages-project-config.json` is preserved when `CLOUDFLARE_ACCOUNT_ID` is unset:

```ts
const envAccountId = getCloudflareAccountIdFromEnv();
const accountId = await requireAuth({
    ...configCache,
    ...(envAccountId ? { account_id: envAccountId } : {}),
});
```

This change is kept solely to preserve the cached `account_id`. Pages commands intentionally do **not** register `--temporary`: the temporary deploy token grants no Pages permissions, so a temporary Pages deploy would only mint an account and then fail.

### Risk

The flag is opt-in and hidden — default behaviour is unchanged. If the upstream preview-account endpoint is unavailable, the underlying HTTP error surfaces as a `UserError` with a static telemetry label.

- Review by ask-bonk[bot]: I reviewed the latest state of this PR (provisioning of a temporary preview account behind the hidden `--temporary` flag). The architecture is solid — the `AsyncLocalStorage` auth-context frame in `runWithAuthContext` plus the single `requireAuth` chokepoint keeps the rest of wrangler untouched, and the two issues from my earlier review (corrupted-cache crash, account-id override loss in Pages) plus Devin's `account_id: undefined` finding are all resolved and covered by tests. Nice work.

One design concern remains that I think is worth addressing or at least documenting explicitly.

### The terms-of-service prompt is interactive but only reachable in non-interactive mode

`ensureAnonymousTermsAccepted` -> `promptForExplicitYes` (`dialogs.ts:98`) is run via the `beforeCreate` hook on cache miss. But the entire anonymous flow is gated on `isNonInteractiveOrCI()`:

```ts
// user.ts:1500
const allowAnonymous = shouldAllowAnonymous() && isNonInteractiveOrCI();
```

So the only time the terms prompt fires is when wrangler has already decided the environment is non-interactive. Yet `promptForExplicitYes` is the one dialog in `dialogs.ts` that does *not* short-circuit `isNonInteractiveOrCI()` — `confirm`, `prompt`, and `select` all return a fallback / throw `NoDefaultValueProvided` in that case, while `promptForExplicitYes` issues a live `prompts()` text prompt and races it against a `stdin` `close`/`end` event.

In a genuinely headless subprocess (the stated target audience — agents driving wrangler with no TTY and no piped answer), `stdin` reaches `end`/`close`, the race resolves to `{ value: undefined }`, the function returns `false`, and the command fails with:

> You must accept Cloudflare's Terms of Service and Privacy Policy to use --temporary.

with no indication of *how* to accept them non-interactively. The only way through is to pipe `yes` on stdin (e.g. `echo yes | wrangler deploy --temporary`), which is undocumented and easy to miss. The unit tests don't catch this because they mock the `prompts` module, so the stdin race is never exercised.

Suggestions (any one of these):
1. Provide a non-interactive acceptance path — e.g. honor an env var like `WRANGLER_ANONYMOUS_ACCEPT_TERMS=yes` or a `--accept-terms` flag — and have `promptForExplicitYes` (or its caller) treat that as acceptance when `isNonInteractiveOrCI()` is true. This is the most robust for the agent-as-subprocess use case.
2. If piping `yes` on stdin is the intended mechanism, make the rejection error message say so explicitly, and add a test that drives a real (non-mocked) `promptForExplicitYes` with a closed/EOF stdin to lock in the behavior.

### Minor

- `versions upload` provisions an account that can deploy a version, but it never surfaces the claim URL with the same prominence the deploy path does — worth confirming `logAnonymousPreviewAccount` output is actually shown for the `versions upload` path in CI (the new test asserts `"Temporary account ready:"`, so this looks fine, just calling it out).
- `getAnonymousAccountConfigFile()` keys the cache by API environment, but `clearCachedAnonymousPreviewAccount()` on login/logout only clears the file for the *current* environment. Switching `WRANGLER_API_ENVIRONMENT` and logging out won't clear a staging/production cache minted under the other environment. Low impact given short TTLs, but worth a comment noting the intentional per-environment scoping of the clear.

Everything else looks good — error paths use static `telemetryMessage` labels, the cache reuse guard checks both `account.expiresAt` and `claim.expiresAt`, and the changeset correctly targets `wrangler` as `minor`.
